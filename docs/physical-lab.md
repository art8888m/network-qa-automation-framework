# Physical lab and device configuration — NET-007-03

## Lab procedure

The owner connected the TP-Link TL-WR740N and TECNO TR118 sequentially through
Ethernet to a Windows ThinkPad T470. Both devices may share the same management
IP; reaching an address cannot identify the connected device.

Before each physical run:

1. Disconnect the previous device and connect only the intended owned device.
2. Verify its model/physical identity locally. Keep identifiers private.
3. Verify the actual management address, active Ethernet interface, DHCP-assigned
   configuration, and route using local Windows inspection. Do not assume values.
4. Set the selected profile's host, timeout, and expected TCP ports in ignored
   `config/devices.yaml`. Review expectations against the current lab baseline.
5. Run only that device's profile, with `--run-hardware` and
   `--confirm-device-identity`, as shown in README. Use one serial pytest session.
6. Review and sanitize results before sharing. Repeat verification after swapping
   devices; never infer identity from a shared IP.

The confirmation flag records the operator's acknowledgement, not programmatic
authentication. The framework never configures routers or changes firmware.

## Configuration and interpretation

`yaml.safe_load` loads only an explicitly selected file. Frozen device profiles
contain host, timeout, and immutable TCP port expectations. Validation rejects
invalid structures, missing/unknown fields, invalid host types, nonpositive or
nonfinite timeouts, invalid port ranges/types, and nonboolean expectations.
Errors omit raw file contents and values. The standard PyYAML safe-loader
semantics apply; quote host strings and use integer keys with true/false values.

Only one exact profile can be selected. Supplying profile options alongside
explicit target overrides is rejected. Multiple devices can be described in one
file, but only the selected device's ports are parametrized. Default runs need
no local configuration and skip the hardware placeholder without socket calls.

The existing boolean TCP API is unchanged. Negative expectations require a
positive port in the profile. Immediately before each negative case, a
function-scoped fixture probes the lowest-numbered positive port, independently
of test order, selection, and `-x`. Failure raises a pytest setup ERROR and the
negative port is never evaluated. No previous positive test result is cached.

Inaccessible still means any socket error, including refusal, timeout, resolution
failure, or unreachable host. Reachability can change between prerequisite and
negative connection attempts. A negative pass cannot prove an explicit refusal
or device identity. A failing prerequisite service blocks negative evaluation
even if another positive port remains reachable. Timeouts bound socket attempts,
not total DNS resolution or multiple-address attempts.

Only synthetic examples are committed. `config/devices.yaml`, local YAML
profiles, packet captures, and generated reports remain ignored. Logs omit
targets and raw exceptions, but pytest tracebacks may show local variables;
sanitize screenshots, logs, and reports before publishing.

The skipped case is the physical connectivity placeholder. New configuration,
selection, and expected-result tests use temporary synthetic YAML and mocked
socket calls, including pytest's in-process runner. Their explicit opt-in flags
exercise test wiring only. The existing real loopback test is local-only.

Prerequisite coverage includes reachable positive/inaccessible negative,
reachable positive/accessible negative, and unavailable prerequisites caused by
timeout, refusal, or generic socket errors. Tests select negative cases alone,
use nonstandard prerequisite ports, and assert that the negative port is never
contacted after prerequisite failure, with and without `-x`. Loader and CLI tests
reject profiles containing no positive TCP expectation.
